Find out whether a "Prettier for prose" exists, and report what it can and cannot reach.

The owner's framing, and it is the right one to work from: Prettier's defining property is not that it
formats nicely. It is that nobody argues about it. You run it, it normalises, the discussion is over.
He wants that for text: a set of rules that pulls any text he or an agent writes closer to a human
reader, applied to documents, README files and code comments alike, without him having to think about
it each time.

So the question is not "what documentation standards exist" - an earlier survey answered that, and the
answer was style guides that an agent must read and interpret. This question is narrower and different:
what runs deterministically over prose the way a formatter runs over code?

WHAT TO COVER, at least:

    Microsoft, write-good, alex, Joblint and whatever else it carries); proselint; textlint and its rule

    what rules does it actually ship, what does a rule fire on, is it configurable-by-default or

  - Whether any of them lints COMMENTS IN SOURCE CODE, not just Markdown. Vale has scoping; find out
    what it really supports and how well. This matters: the owner's corpus is 3,000 lines of comments
    inside JavaScript, not only prose files.
  - Agent skills that act as a normalising pass over any text rather than as advice about writing: a
    prose "prettifier" the agent runs at the end of every piece of writing.
  - The boundary, which is the most useful part of your answer. These tools catch surface properties:
    sentence length, passive voice, weasel words, jargon lists, readability scores. State plainly, with
    examples, what class of defect they provably cannot reach.

A CONCRETE TEST OF THAT BOUNDARY. A human reader recently found six defects in one rewritten opening
paragraph of this repository's README, and ten specialised agents plus two judges had missed all six:
  1. definitions placed before the reader had a reason to care about the terms;
  2. an environment-variable name in the first paragraph, meaningless to a newcomer;
  3. the subject narrowed to "coding tasks" when the plugin takes any work, which made it false;
  4. the statement of the project's purpose deleted entirely;
  5. a property of the implementation promoted to the opening as if it were the purpose;
  6. the wrong thesis: it argued why to use the thing instead of saying what it is.
For each of these six, say whether any tool you found would fire on it, and name the rule that would. Be
strict: "a sentence-length rule might have caught it" is not a yes.
