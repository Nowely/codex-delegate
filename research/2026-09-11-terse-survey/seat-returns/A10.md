## Practices

- **Be clear and direct — G, [P][P].** Specify outputs, constraints, scope, and ordered steps. R: copy the existing protocol’s link-following restriction into the brief: “Follow only links encountered from the entry file; report ‘not found’ when unsuccessful.” Define whether repeat opens count as steps. J: supply the claim ledger, protected passages, and prerequisite inventory needed to apply its rows.
- **Explain the purpose — G, [P][P], [F][F].** Give the reason behind consequential instructions. W already explains that measured failures drive the rewrite; retain that. J: “Length only breaks ties because shorter text can omit a necessary condition.” Adding the experimental purpose to R would change its protocol; test separately.
- **Use multishot examples — G, [P][P].** Supply 3–5 relevant, diverse examples, including edge cases, inside `<examples><example>…`. J: demonstrate a new-lie veto, weakened-warning veto, successful repair, and attractive but unrepaired draft. W: show a repair preserving a condition. Keep project answers out of R’s examples. The example count is advice, not a reported measurement.
- **Separate inputs with XML — G, [P][P].** Tag instructions, context, examples, and variable inputs consistently. W: wrap its four parts in `<reader_profile>`, `<writing_rules>`, `<prerequisites>`, and `<measured_failures>` without changing their text or order. J: distinguish `<rubric>`, `<candidate>`, and `<code_evidence>`. Tags aid parsing; they do not enforce access rights.
- **Set a role — G, [P][P].** Put a concise task role in the system prompt where the runner exposes it. W: “You repair documentation against observed reader failures.” J: “You independently assess candidate claims against supplied evidence.” R already specifies a first-time reader; an expert persona would change the population being simulated.
- **Put long documents first — M, [P][P], “Long context prompting.”** For 20k+ token inputs, place documents and source metadata before instructions/examples, with the query last. Exact report: “Queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs.” No model breakdown, metric definition, sample size, or test protocol is supplied. Apply experimentally to large W/J inputs; do not preload R’s repository.
- **Quote before answering — G, [P][P], “Long context prompting.”** Extract relevant quotations before performing the task. J: “First collect candidate and code lines relevant to this row; then decide.” W: collect the failed line and supporting behavior before repairing it. R already requires a quotation, but after its answer; moving it first is a new measurement condition. The 30-percent claim concerns query placement, not quotation extraction.
- **Use chain of thought selectively — G, [P][P].** With thinking disabled, manual step-by-step prompting is a fallback; separate the explanation from the answer. J can assess rubric evidence before scoring. Do not add lengthy reasoning to baseline R. On Fable models, do not ask for reproduction of internal reasoning; [F][F] warns this can trigger refusal. A concise evidence justification is sufficient for the sheet.
- **Tune extended/adaptive thinking — M/G, [P][P], [O48][O48], [O5][O5], [S][S], [F1][F1].** Use supported thinking modes, sweep effort on actual tasks, and allow output headroom. P reports: “In internal evaluations, adaptive thinking reliably drives better performance than extended thinking”; no figures follow. Prefer general reasoning guidance over a prescribed mental script. W/J may benefit; preserve R’s model, effort, token allowance, and prompt when comparing documentation versions.
- **Replace prefilling where unsupported — G/API constraint, [P][P].** Current guidance says last-assistant-turn prefills return 400 on models starting with Claude 4.6; older models retain support. R/J: ask directly for required fields, or use a supported output schema. “Return only these fields…” specifies formatting without inserting an answer. No evidence that terse currently prefills.
- **Chain inspectable stages — G, [P][P].** Use separate calls when intermediate outputs must be inspected, logged, or branched; its example is draft, review, refine. W’s saved passes and J’s independent reviews serve that purpose, although four passes within one writer invocation are not four API calls. A literal implementation would call each pass separately and pass its artifact onward; benchmark before changing orchestration. R remains one fresh reader per question.
- **Use templates and variables — U for the old page; illustrative examples in [P][P].** Keep instructions stable and substitute explicit inputs. W: replace hardcoded “Six fresh readers” with the actual count; parameterize file, angle, profile, and failures. R already parameterizes repository, entry file, and question. J should parameterize candidate and evidence. I could not recover the old page’s guidance or measurements.

The notebook was not opened because its host is outside the named fetch hosts; no generator performance claim was recoverable here.

- **Specify positive style and necessary detail — G, [P][P], [O5][O5], [F][F], [F1][F1].** Describe desired output, use positive examples, and make the prompt’s style compatible with the deliverable. W: “Use complete, direct sentences; include each condition where the reader decides; omit details that change no decision.” F1 recommends literal language over mannered metaphors; O5 says effort does not reliably shorten visible output. - **Bound scope and finish authorized work — G/M, [P][P], [O5][O5], [F1][F1].** Specify allowed actions, completion criteria, and stopping points. - **Control delegation and verification — G/M, [P][P], [O5][O5], [F][F], [F1][F1].** State which seats may spawn agents and cap counts. - **Preserve state without contaminating readers — G, [P][P], [F][F], [F1][F1].** Keep structured results, exact constraints, and progress across long runs; preserve conversation history and thinking blocks as required by the API. W/J: keep artifacts and evidence references in the run directory. Cross-question memory is inappropriate for R. Append-only history, compaction, progress-display settings, fallback handling, and identity configuration are runner concerns, not additional reader questions.
- **Review broadly, then adjudicate — G plus model evaluation claim, [O48][O48], [S][S], [O5][O5].** Avoid vague instructions that suppress lower-severity findings. Uncertain allegations must not automatically become vetoes.
- **Use self-checks according to the model — G, [P][P], [O5][O5].** P suggests verifying against explicit criteria; O5 advises removing redundant checks because they add cost without improving results. W/J should deliver evidence required by the contract, with no generic “double-check everything” loop. Do not add self-correction rounds to baseline R or confuse self-checking with independent documentation measurement.
- **Apply domain-specific presentation tools where relevant — G/M, [P][P], [O48][O48], [S][S], [F1][F1].** Give visual tasks crop/zoom tools and concrete design directions; request math formatting and document templates explicitly. P reports “consistent uplift on image evaluations”; O48/S report 1080p “provides a good balance of performance and cost,” without scores. These visual/frontend techniques do not apply to the three Markdown-focused prompts.
- **Reason against the rubric before scoring — G, [E][E].** J: “Assess the cited evidence against each criterion first; then emit the two veto decisions and the remaining scores.” E says this increases evaluation performance, especially for complex judgment, but reports no measurement. Keep evidence and concise decision justifications in the sheet; exclude deliberation from the score. This changes judging without coaching the measured reader.

## contradictions

- **Reasoning versus the reader construct:** CoT, retries, self-correction, expert roles, or answer-bearing examples can improve answers while leaving documentation unchanged. One API request can still be one-shot while spending much more reasoning. Such changes require a fresh baseline and cost/latency accounting; they cannot be credited as documentation repairs.
- **Documents-first versus discovery:** Preloading documents or a supplied index contradicts R’s entry-file/link-following experiment and removes findability from the test. The long-context recommendation concerns supplied large inputs, so R’s tool-driven workflow is not automatically defective. If W’s failure evidence becomes large, moving it ahead of rules would conflict with its fixed four-part order; test that alternative explicitly.
- **Quote-first versus quote-last:** R’s listed output starts with `answer` and ends with `quote`. It agrees on evidence collection but does not require Anthropic’s evidence-before-answer procedure. Quote-first may prevent a wrong answer instead of merely diagnosing it; that benefit changes the measuring instrument.
- **Fixed wording versus model tuning:** W freezes rules and pass order; current guides recommend retiring overly prescriptive instructions and tuning language per model. Positive-style/context guidance also pulls against its largely prohibitive rules and some metaphorical wording. These are preferences and experimental tensions, not proof the four-pass method is wrong; inspectable stages are expressly supported.
- **Fixed panel versus model-dependent verification:** O5’s advice against extra verification agents conflicts with a mandatory two-judge bake-off if treated as universal. F’s fresh-verifier advice supports independent scrutiny instead. Neither finding justifies removing terse’s judges or asserting that the bake-off improves outcomes without a local comparison.
- **Freshness versus persistent agents:** F’s reusable agents and memory conflict with sharing reader context across questions. Keep those efficiencies to coordinating/writing work; preserve independent judge sheets. Proactive source/web research likewise conflicts with R’s restricted evidence domain, while agreeing with W/J’s truth checks.
- **Small visible test set versus generalization:** E favors volume and held-out evaluation; terse uses five to eight questions, exposes failures to writers, and reuses the questions for regression. That measures repair of those failures, not performance on unseen reader decisions. Different-generator/grader guidance is also not guaranteed by terse’s default Claude-only pool. Add validation outside the existing regression score.
- **No conflict on clarity self-report:** P’s “colleague with minimal context” check concerns whether a human can follow the prompt; E’s external rubric grading concerns outputs. Neither asks the measured reader to report whether documentation felt clear. Keep terse’s exclusion of that self-report.

## evaluation

- **Establish success before tuning — [O][O], [E][E], G.** Start with a draft, explicit success criteria, and empirical tests. Make criteria specific, measurable, achievable, relevant, and multidimensional: accuracy, consistency, context use, latency, and price. For terse, retain correctness/controls/departures and add measured token cost and response time; never reveal the answer key to R.
- **Broaden cases — [E][E], G.** Match the real task distribution; include absent/irrelevant inputs, long inputs, ambiguous cases, paraphrases, typos, and misleading framing. E explicitly says “Prioritize volume over quality” for scalable automated evaluation and suggests generating cases from seed examples. Validate generated keys against code; keep a held-out set away from writers. This is my application of their principle.
- **Calibrate graders — [E][E], G.** Prefer reliable code grading for categorical outputs; use LLM grading for nuanced correctness only after checking reliability. Use detailed rubrics with binary decisions or anchored scales; multiple rubrics may be necessary. Its examples recommend a different evaluating model, despite using the same model string in sample code. Blind candidate labels alone do not provide model independence.
- **Borrow methods selectively — [E][E], G.** Examples cover exact-match accuracy, embedding cosine similarity for consistency, ROUGE-L for summaries, Likert tone ratings, binary privacy classification, and ordinal context use. Similarity or prose ratings cannot replace terse’s code-derived correctness key. Example datasets/targets—such as F1 ≥0.85 on 10,000 posts—are illustrations, not reported achieved results or required sample sizes.
- **Compare treatments cleanly — [P][P], [O48][O48], [S][S], [F1][F1], G.** Re-check advice on the actual model; sweep effort and assess quality/cost. O48/S suggest recall or F1 when tuning review harnesses; S says match observed thinking length rather than effort labels across models. Keep prompt/model/budget fixed for a documentation comparison, and benchmark prompt changes separately.
- **Guard against teaching only the test — [P][P], G.** Its coding guidance says to solve the general problem, not hardcode test inputs. W adaptation: “Repair the underlying explanation and route for equivalent reader questions, not merely the measured wording.” No fetched page establishes terse’s pool size, six-question reliability, or the causal contribution of its four passes. No terse experiment was run for this report.
