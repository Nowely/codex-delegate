Codex gpt-6-astra A3 opened GitHub, Algolia, Elastic and PostHog source files, Write the Docs publication text, and GSoD case studies; verdict: continuous signals can trigger audits, but executable checks provide the earliest direct evidence of rot.

“None found” below means in the material opened, not that no organisation publishes one. Repository text was read; recordings and live analytics were not. Passive telemetry needs real users, but no hired reader or model evaluator.

**1. Search telemetry**
Counts: zero-result rate = searches returning zero hits / searches; Algolia also exposes no-click searches / searches with click tracking.
Opened: Algolia’s [zero-results API specification](https://github.com/algolia/api-clients-automation/blob/main/specs/analytics/paths/search/getNoResultsRate.yml), description and response fields, and [no-click specification](https://github.com/algolia/api-clients-automation/blob/main/specs/analytics/paths/search/getNoClickRate.yml).
I did not verify a team’s refinement or search-exit formula. Implementable definitions are: search episodes containing reformulation / search episodes; episodes ending on results without a result click / search episodes. These are proposed conventions, requiring explicit session boundaries.
Bias: query prefixes, filters, bots and index failures can inflate zero results; reformulation can be exploration; no click or exit can mean the result preview answered the question. These signals do not establish textual incorrectness.
Published action threshold: **none found**. Human/model: neither for counting. Rot alarm: useful after renamed concepts or broken indexing; weak for an incorrect page that remains discoverable.

**2. Support gaps and ticket deflection**
Opened: WTD’s [support-team guide](https://github.com/writethedocs/www/blob/main/docs/guide/writing/support-team.rst), “Simplify communication” and “Collaborate”: support forwards recurring issues, then reviews the resulting documentation to verify it answers them.
For attribution, count distinct support cases linked to a confirmed missing, incorrect or hard-to-find explanation; that taxonomy is my recommendation. Human classification establishes the gap; a ticket containing a documentation link alone does not.
Opened: GitHub’s [exits-to-support query](https://github.com/github/docs/blob/main/src/metrics/queries/exits-to-support.ts), entire query: it counts qualifying support-link clicks / external-link clicks, excluding one upgrade destination. **It does not count tickets prevented.**
Defensible computation, recommended: randomly compare old/new documentation among eligible users; let \(r\) be the proportion creating a relevant ticket within a fixed follow-up window; relative deflection = \(1-r_\text{new}/r_\text{old}\). Report both denominators, uncertainty, delayed contacts and other support channels.
Bias: user growth, product fixes, contact friction and reader self-selection confound before/after ticket totals; visits divided by tickets is not causal deflection. Threshold: **none found**. Human: attribution/validation; model: unnecessary. Rot alarm: specific but usually late.

**3. Time on page and scroll depth**
Opened: GitHub’s [event implementation](https://github.com/github/docs/blob/main/src/events/components/events.ts), `trackScroll`/`sendExit`, and [duration query](https://github.com/github/docs/blob/main/src/metrics/queries/view-duration.ts): elapsed seconds to an exit signal; maximum viewport-bottom position / document height; reported duration averages daily medians.
Opened: WTD’s [July 2024 newsletter](https://github.com/writethedocs/www/blob/main/docs/blog/newsletter-july-2024.rst), “How to think about docs metrics”: low duration can mean either the wrong page or an answer immediately found; metrics cannot distinguish navigation from content problems.
Bias: scrolling measures exposure rather than comprehension; viewport size, anchor jumps, page length and interrupted sessions change results. Published cautions are qualitative, not quantified bias estimates.
Threshold: **none found**. Human/model: neither for collection; interpretation needs context. Rot alarm: weak alone; useful for investigating a page whose behaviour changes after a release.

**4. Thumbs and “was this helpful?”**
Opened: GitHub’s [survey-score query](https://github.com/github/docs/blob/main/src/metrics/queries/survey-score.ts): latest response per user/page, excluding AI-answer votes; score = `(positive votes + 0.75×30)/(votes + 30)`, then rounded.
Response rate should separately count respondents / eligible exposed readers; page views are a poorer denominator when the widget is not seen. **No observed helpfulness-widget response rate was verified.**
Opened: WTD’s [December 2019 newsletter](https://github.com/writethedocs/www/blob/main/docs/blog/newsletter-december-2019.rst), “Documentation feedback widgets”: community members report possible negative self-selection, unactionable downvotes, and fewer responses when commenting requires more effort.
Opened: PostHog’s [documentation engineering post](https://github.com/PostHog/posthog.com/blob/master/contents/newsletter/what-nobody-tells-devs-about-docs.md), section 2: its team reviews votes alongside replays, questions and support issues **weekly**.
Threshold: **none found**; GitHub’s 75% prior and 30 pseudo-observations are not action thresholds or sample sizes. Human: voters and diagnostic follow-up; model: unnecessary. Rot alarm: a specific error report can be excellent; aggregate sentiment is weaker.

**5. Completion measured in the product**
Opened: PostHog’s [per-product activation handbook](https://github.com/PostHog/posthog.com/blob/master/contents/handbook/growth/growth-engineering/per-product-activation.md), query structure and interpretation: first intent per organisation, qualifying product events within 30 days, then retention at three months; materialised views keep counting inexpensive.
This verifies production event-based outcome measurement, **but not a join from a particular documentation page to its task**. That requested documentation-specific implementation remains unverified.
For terse, the required measure would be eligible readers subsequently emitting the page’s success event / eligible readers, within a declared window, segmented by product/version and prior completion.
Bias: product faults, permissions, identity loss and reader selection can change completion independently of prose. Published trigger: PostHog investigates onboarding when monthly activation trends decline; **no numeric cutoff found**.
Human/model: neither for established event joins; humans must define the task and eligibility. Rot alarm: potentially early after release, but requires traffic and diagnosis.

**6. Executable documentation checks**
Opened: Elastic’s [8.19 documentation guide](https://github.com/elastic/elasticsearch/blob/8.19/docs/README.asciidoc), “Test code snippets”: console examples become isolated tests; response bodies and expected warnings are checked against the product.
Count failing assertions, executed examples and skipped examples separately. Published failure condition: an unexpected or missing expected warning fails the test; response assertions detect changed behaviour.
Bias: selective coverage, hidden setup, substitutions and skipped assertions can conceal drift; Elastic explicitly warns substitutions can make a snippet “lie.”
Opened the corresponding [current guide](https://github.com/elastic/elasticsearch/blob/main/docs/README.md): it says snippet testing is temporarily disabled during migration. Published machinery is not proof of current operation.
Human/model: neither at runtime after authoring assertions. Rot alarm: **earliest for covered claims**, potentially on the breaking commit before any reader arrives; cannot assess explanations or findability.

**7. Controlled page experiments**
Opened: GitHub’s [content A/B-testing guide](https://github.com/github/docs/blob/main/src/events/components/experiments/content-ab-testing.md), authoring, tracking and analysis sections: serve original/rewritten content, attach variant to impressions, clicks and exit events, and compare per article.
Counts: outcome events relative to exposed users/impressions, using a consistently chosen unit. Bias: CTA clicks are not product completion; experiment assignment and event coverage need checking.
Published threshold: sequential significance testing with configurable minimum detectable effect, but **no numeric decision rule accessible**. Human: experiment design; model: unnecessary. Rot alarm: validates proposed repairs rather than detecting unknown drift unaided.

**8. Repeated answer-engine checks**
Opened: Sarah Lin’s MongoDB [WTD 2026 abstract](https://github.com/writethedocs/www/blob/main/docs/_data/portland-2026-sessions.yaml), “How to Win Docs and Influence Robots”: repeated prompts across answer engines, with reported accuracy below.
Count: answer accuracy, but scoring rubric and denominator are absent. Bias: retrieval and model changes can move scores independently of documentation. Threshold: **none found**.
Human: scoring/oracle requirements unspecified; model calls: **yes**. Rot alarm: possible semantic regression signal, but not a cheap deterministic replacement for terse.

For terse, my recommendation is commit-triggered executable checks first, then version-specific search/completion/feedback trends to select re-audits; telemetry cannot detect rot on unread pages.

## numbers

- MongoDB reports **93% accuracy across approximately eight answer engines**; number of prompts, answers, repetitions and before/after observations **not supplied**. Abstract-only evidence, not a verified page-change effect.
- PostHog reports **49+ revisions to one Next.js documentation page**; reader sample and outcome effect absent. This measures maintenance activity.
- PyTorch-Ignite’s [2021 case study](https://github.com/pytorch/ignite/wiki/Google-Season-of-Docs-2021---Case-Study), “Metrics,” reports **eight merged community PRs**, while postponing quantified documentation outcomes; PRs are not reader successes.
- **The requested page-change case with a ticket/search/completion effect and sample size was not verified.** Opened NumPy, SymPy and Ignite cases mainly measured delivery or deferred outcome measurement; I found no defensible numerical benchmark to substitute.
